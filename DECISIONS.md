# Decisions

One entry per rule, with the reason. Add to this whenever a rule changes.

## 20 October 2026

- **Grids are official, fixed, and computed here.** A catalog beach's anchor, heading, cell size, and cell set are computed once by this pipeline. The app registers that grid as a Space on arrival and never generates cells. Reason: the grid must be the same for everyone at a beach, not whatever the first phone minted. Ad hoc stretches off the catalog keep the old phone-made grid.
- **Grids are shaped to the sand.** Cells are 5 m, run along the shore, and exist only inside the mapped outline. A grid is never a bounding square.
- **Keep every OpenStreetMap tag.** The raw tag map is stored on each beach next to the extracted fields. Reason: we do not know yet which tags the app will want.
- **Capture the keys OSM uses.** Element type, id, version, timestamp, changeset, and ready-made links to the element, its edit page, Wikidata, and Wikipedia. Reason: the app deep links to the source, and the diff can point at the changeset that moved a beach.
- **Hash by block, with a cadence per block.** Blocks: geometry, nearby, stations, places, land, weather, wiki, terrain. Each has its own hash per beach and its own re-pull interval. Reason: a webcam appearing must never invalidate a grid, and a yearly run should skip what has not changed.
- **The pack files are the cache.** A beach whose block hash matches the previous committed pack is reused from it. There is no separate cache folder. Reason: a cache folder duplicated the pack and would be hundreds of megabytes nationally.
- **Overpass runs in its own queue.** Tile fetches from OpenStreetMap run independently of every other source and can run at the same time. Reason: Overpass is slow and unreliable under load and must not block the rest.
- **PAD-US is downloaded whole.** The public land dataset is pulled once and looked up locally, not queried per point. Reason: the per-point service took up to 96 s per beach and is hosted on an account that could move.
- **EPA BEACON is dropped.** Reason: it is live advisory data, not catalog data, and there is no stable list of monitored beaches with coordinates.
- **Pull webcams, surf spots, and surf shops that OSM has.** With all their tags, attached to beaches within 300 m. Reason: the app opens a publisher's own camera page and wants to name the break.
- **Packs fold by country, then state, and ship as SQLite.** JSON per state is committed and reviewed. A per-state SQLite file, gzipped, is the phone download, with an index of size and hash per state. Reason: the phone already runs SQLite, opens the file read-only, and queries it without parsing anything up front.
- **Packs are pulled from this public GitHub repository.** Release assets, one release per pack build.
- **Spaces are seeded for primary beaches only.** Reason: seeding tens of thousands of empty spaces would clutter discovery.
- **Terrain comes from USGS 3DEP, quantised per cell.** One height per cell, rounded to 0.1 m, relative to the beach's lowest cell, baked into the grid rows, with the datum offset to the tide station and the flight date per beach. Fetched one 20 km raster per cluster at 5 m. Reason: the phone colours the tide per cell and draws slope without touching a raster. AR measurement on the sand still wins.
- **Spaces are shown on a map on the phone.** Boundaries are stored as latitude and longitude rings so they draw over a map view without conversion. Reason: people need to see where a stretch is before they are standing on it.
- **Packs are served from GitHub Pages at well-known paths.** `https://packs.beachx.apphaus.us/index.json` and `/<country>/<state>.sqlite.gz`, a custom domain on Pages. A GitHub Action builds the SQLite files on a tag and publishes them; the same tag gets a release with the files as the archive. Reason: the phone asks a fixed URL and never knows about tags.
- **Cells carry water distance, volatility, slope, and buildable flags.** Computed from the boundary edge that meets the coastline, the height above the tide datum, and the outline, stored in the grid rows beside the height. Reason: tide colour per cell and refusing a castle on sand that will not hold are lookups, not judgements the phone makes.
- **Overlapping OSM features are merged into one beach.** Same sand mapped twice becomes one record carrying both OSM ids. Genuinely different beaches that share an edge stay two polygons, drawn overlapped on the map, and a cell belongs to the space the person registered.
- **Unnamed beaches get a generated name.** "Unnamed stretch near <place>" from the places block.
- **The admin map view is the review tool.** An admin can mark a beach wrong with a reason and a corrected name or tier. Corrections go to an overrides file in this repo, keyed by beach id, applied at build, so they survive a re-pull.
- **Licences.** Code is MIT. `pack/` is ODbL, attributed "© OpenStreetMap contributors". Wikipedia descriptions stay, each attributed with its source URL under CC BY-SA 4.0. The app shows the OSM attribution in Settings and on the map view. See LICENSE.
- **The app uses native maps.** Apple Maps on iOS, Google Maps on Android, with the pack's boundary drawn on top and attributed.
- **The backend is Cloudflare.** Workers for the thin sync endpoint, D1 for the rows. A space for a catalog beach stores the beach id and pack version, never a copy of the anchor or grid. Pack files are served from Pages, not the backend.
- **Cell claims and placements are never in a pack.** Packs are catalog data only; claims live in the app database and sync to the backend.
- **Impersonation for development.** An admin-only setting makes the app read a chosen beach or point instead of GPS. Local mode is forced on, surf votes are not recorded, diagnostics carry a flag and no coordinates, and an amber banner shows the pretend place on every tab. Admin mode is always on in debug builds and unlocked by a code in release builds. The review-queue actions sit behind the same gate.
- **Camera thumbnails follow a rights field.** Each camera record carries `rights`: `unknown`, `public_domain`, or `permitted`. Unknown shows a generic tile and fetches nothing until tapped, which opens the publisher's page. Public domain and permitted show the still with the source or publisher credited on the tile. A still is never hot-linked when rights are unknown. Reason: the app has no agreement with most publishers, and a government feed needs none.
- **Cell record, decided 20 October 2026.** One fixed 8-byte record per cell inside the boundary, no spans: `height int16` in 0.1 m relative to the beach's lowest cell; `water int16` in 0.1 m from the cell centre to the nearest water-edge segment, 0 means the cell touches the water edge, clamped at 3276.7; `volatility uint8` 0 wash (below mean high water), 1 wet (to the highest astronomical tide plus the beach's wave margin), 2 dry (above), 3 back (dune, vegetation, wall), 255 unknown; `slope uint8` in whole degrees 0 to 90 from the steepest neighbour, 255 unknown; `flags uint8` bit 0 build (wet or dry, sand, slope at most 10°, fully inside the boundary), bit 1 edge (the cell straddles the boundary polygon); `reserved uint8` zero. There is no touches_water field, water 0 says it. Little-endian. The grids table stores a `rows` blob of `[y int16, x0 int16, count uint16, count × record]` repeated, and the manifest carries `cell_record_version: 1`. The water edge is the boundary where it meets the OSM coastline or lake polygon, and +y on every grid points up the beach. Reason: whole bytes read and debug more easily than packed bits, slope in degrees keeps its meaning, and the phone slices one row per 8 × count with no decoding. Hawaii is 524,514 cells, about 4 MB before gzip. Open: whether wash cells are placeable with a warning or refused.
- **No full national pull yet.** Requirements are still arriving. Hawaii is the only pack built.
- **PAD-US is read from the state zip's Combined KMZ.** ScienceBase publishes each state as a file geodatabase plus KMZ layers, not a GeoPackage, so the build reads the Combined layer's KML (WGS 84, attributes in each placemark's table) with zipfile and ElementTree, and decodes the manager and designation codes from the coded-value domains stored as XML in the geodatabase's item table. The paged export of the PAD-US Public Access feature service over the state's box is the fallback. The zip is kept in `raw/downloads/padus/` and every beach, any tier, is looked up locally within 30 m. Reason: no GeoPackage exists per state, and KML needs no projection or binary geometry parser. Hawaii's primary count rose from 56 to 83 because every beach now gets its PAD-US points, not just ten.
- **Merging needs agreeing names.** Two polygons are the same sand when half of the smaller lies inside the larger; a node or open way is the same sand as a polygon it lies inside; two same-named pins within 100 m are the same. They merge only when the names agree or one side is unnamed, and an unnamed outline that touches two or more different names merges with none of them. The primary member (polygon, largest, named, way before relation before node, lowest id) gives the id, tags, and fields; gaps are filled from the others, every member is listed in `osm_ids` and `merged_from` with its tags, the boundary keeps every member's rings with `parts` saying which rings belong together, the grid is the union of the members' cells, and the area is the union estimated on a lattice. Reason: in Hawaii one unnamed outline under Mokulēʻia carries five named beach pins, and collapsing them would delete four real beaches. Hawaii goes from 472 elements to 463 beaches.
- **Generated names come from the Census Gazetteer.** `display_name` is the OSM name, else "Unnamed stretch near <place>" with the nearest incorporated place or census designated place (its LSAD suffix such as "CDP" dropped) from the national Gazetteer file, downloaded once, within 30 km, else "Unnamed stretch". `name` stays the OSM name or null, so an unnamed beach is still minor and still skipped by the Dart seed. Reason: the Census geocoder in the places block only runs for primary and secondary beaches, and unnamed beaches are always minor, so it never answers for the beaches that need a generated name.
- **Water comes from a third Overpass query per tile.** `osm_water` returns every `natural=coastline` way and every water polygon (`natural=water`, `waterway=riverbank`) within 500 m of a beach in the tile, with full geometry, guarded by the same `around` canary as the nearby query. It belongs to the geometry block, and a beach's geometry hash covers the water features near it with their kinds, so a moved coastline recomputes the grid and an unchanged one reuses it.
- **The water edge is where the boundary has water on its outside.** A boundary segment is water edge when, for at least half of its sample points (every 2.5 m), a point 1, 5, or 10 m outward (away from the beach) is in the water: on the coastline's water side or inside a water polygon. Consecutive segments form the polylines stored as `water_edge` on the boundary. Reason: OSM beach outlines often share the coastline's nodes, many are drawn a few metres off it, and many are drawn seaward of it (between high and low water); "near the coastline" picked the landward side of those, "water outside" picks the seaward side of all three.
- **Water kinds.** `sea` for the coastline, for water tagged lagoon, harbour, bay, salt, or tidal, and for any water polygon whose outline comes within 10 m of the coastline (it opens to the sea); `river` for riverbanks and river-like `water=*`; `lake` for other water. Great Lakes coastline is `lake`. A lake or river beach has no tide station. Reason: Hawaii's Ko Olina and Magic Island lagoons are untagged `natural=water` polygons that are tidal; without the coastline test they came out as lakes with no tide.
- **+y points up the beach, so the heading turned 90°.** The grid heading is the direction away from the water, in [0, 360): the opposite of the length-weighted water-side normals of the coastline and water outlines within 60 m of the beach. Which side is water comes from the water itself: the OSM coastline keeps land on its left, and a water polygon holds its water inside. +x runs along the shore and rows are bands parallel to the water. With no water within 60 m, or when the normals cancel (an islet, a spit), the direction from the beach's centre to the nearest water within 500 m is used (`orientation` `nearby_water` or `ambiguous_nearby`); with no water at all, +y is across the outline's long axis with an arbitrary sign (`outline`). Reason: the old heading was the outline's long axis, so +y ran along the shore; and many OSM beaches are drawn seaward of the coastline (between high and low water), where the outline meets the coastline on its landward side, so the outline's own normals pointed 21 Hawaii grids out to sea.
- **Water distance is measured to the water edge.** A cell's water value is the distance from its centre to the nearest water-edge segment, or, for a beach with no water edge (set back more than 10 m from the water), to the nearest coastline or water outline; 0 within one cell (5 m). Cells are never zeroed for lying on the coastline's water side, because OSM coastlines in Hawaii are often drawn at the vegetation line with the whole beach seaward of them. Reason: with rows parallel to the shore the edge usually runs between the first row's centres and the outline without crossing any cell's square, so "crosses the square" left whole beaches with no cell at the water.
- **Terrain is sampled at cell centres from 3DEP pieces.** Beaches are clustered greedily into boxes of at most 20 km a side. Each cluster's raster is asked of the 3DEP dynamic image service in Web Mercator (so 5 m ground pixels stay square at any latitude), float32 GeoTIFF with LZ77, and read by a stdlib GeoTIFF reader; every cell centre is sampled bilinearly. The full 4000-pixel export timed out (HTTP 504 after ten minutes), so a cluster's raster is fetched as pieces of at most 1000 pixels with a 2-pixel overlap, and only the pieces over a beach. Heights are kept per beach in `raw/<state>/<run-date>/terrain/` with the grid key (a hash of the anchor, heading, and cell set) they were measured for, and the raster pieces are kept beside them, so a grid that changes later in the same run (new rules, an override) is measured again without the network. The terrain block carries that grid key; a beach whose grid changed has no heights until the next terrain pull, which takes exactly those beaches. Project name, resolution, and flight start and end dates come from the finest 3DEP catalog dataset under the beach's lookup point.
- **The terrain datum is NAVD 88, or local mean sea level where NAVD 88 does not exist.** Hawaii, Puerto Rico, the Virgin Islands, and the Pacific territories are read as local mean sea level. Reason: the 3DEP catalog labels Hawaii's lidar NAVD 88, but its hydro-flattened sea reads 0.0 at Waikiki, which is local mean sea level.
- **Tidal datums come from the beach's tide station, or its reference station.** A subordinate prediction station publishes no datums, so its reference (harmonic) station answers, and `tide_datum_station_id` names it. The beach keeps differences that do not depend on the station datum: mean high water above mean sea level, above NAVD 88 (null where it is not tied in), and the highest astronomical tide above mean high water.
- **The wave margin is half the typical wave height.** Typical is the median significant wave height (WVHT) over the last full calendar year of NDBC history at the nearest buoy within 100 km that reports waves (the nearest buoy may only report weather), then the year before, then the 45-day real-time file. The margin is half the median, clamped to 0.2 to 2.0 m and rounded to 0.1 m. Without such a buoy the default is 0.5 m on the sea and 0.3 m on a lake or river; a lake or river beach never takes an ocean buoy. Reason: half of the significant height is a conservative stand-in for run-up on a sandy beach, and Hawaii's buoys give 0.4 to 0.9 m.
- **The water surface is read off the raster.** `terrain_water_m` is the median height 15 m seaward of the water-edge vertices, where lidar is hydro-flattened. A lake or river beach uses it as its mean high water, because there is no tide station on a reservoir; when it is missing the lowest cell stands in.
- **How the cell record is filled.** Height is the cell's 3DEP height in 0.1 m above the beach's lowest cell, -32768 when the raster has no value there. Water is clamped at 32767, which also stands for "no water within 500 m". The beach carries `datum_offset_m`, the lowest cell's height above the tide station's mean high water in the terrain's datum, so a cell is `height / 10 + datum_offset_m` metres above mean high water, and `wet_limit_m`, the highest astronomical tide above mean high water plus the wave margin (the wave margin alone on a lake or river). Wash is below mean high water, wet is up to `wet_limit_m`, dry is above. Back is a dry cell that rises at least 20° from the cell on its water side (y - 1), and every dry cell above it in the same column: the dune face, wall, or cliff and what lies behind it. Slope is to the steepest of the eight neighbours, from the unrounded heights. Build needs wet or dry, a beach `surface` that is absent or `sand` (OSM assumes sand on a beach), a known slope of at most 10°, and no edge. Volatility and slope are 255 without terrain or without tidal datums. Reason: the phone then needs one addition and one comparison per cell, and a 20° rise against the cell below marks the dune face itself, not the flat sand at its foot.
- **The grids JSON stores the rows blob as base64.** `grids.json` keeps one line per beach with the frame, the bounds, `cell_record_version`, and `rows`, the same bytes the SQLite file stores. `python3 -m beachx_pack show --state HI <beach id>` prints a beach's rows decoded. Reason: Hawaii's 524,000 cells as JSON arrays would be about 10 MB per state and diff no better than one changed line per beach.
- **A state is the unit of work.** Every command takes `--state XX`. Raw files go to `raw/<st>/<run-date>/` and the pack to `pack/us/<st>/` (lower-case postal code; Puerto Rico and the Virgin Islands also sit under `us`), so two states can be pulled and built at the same time. Whole-file downloads shared by every state (PAD-US by state, TIGER, the Gazetteer) live in `raw/downloads/`. `pack/index.json` lists every state pack and is merged on write. A coastal state walks its hand-written coastal tiles; a state without any (Kansas) walks 2° tiles on even degrees over its TIGER box, and the state box table now covers all 50 states. Reason: two agents run Kansas and California next, and a state is what the phone downloads.
- **States are assigned by the Census TIGER/Line state polygons.** The national 2024 state shapefile is downloaded once and read by a small shapefile reader. A beach belongs to the state whose polygon holds its lookup point (`state_confidence` `tiger`); one outside every state but within 2 km of the target state belongs to it (`tiger_near`); every other beach in the tiles is left to its own state's run and counted as `other_state`. The Census geocoder's state no longer overrides the state. Reason: TIGER/Line polygons include coastal and territorial water, so a beach on the shore is inside its state; the answer is local, covers every tier, and decides which folder a beach lives in. The Overpass state areas stay in the beach query only as a check on silently partial answers.
- **Inland time zones.** Each added inland state takes the zone most of it keeps; Kansas's Sherman, Wallace, Greeley, and Hamilton counties and Texas's El Paso and Hudspeth counties are America/Denver. Other inland splits (Nebraska, the Dakotas, Kentucky, Tennessee, Idaho) are left for when a lake beach lands on the other side.
- **`dist/` mirrors the Pages root.** `python3 -m beachx_pack dist --state HI` writes `dist/us/hi.sqlite.gz` and merges its entry into `dist/index.json` (path, gzipped size, SQLite size, sha256, pack hash, beach, grid, and cell counts, `cell_record_version`, `schema_version`, run date, built date). Tables: `manifest` (one row), `beaches` (the fields the phone filters on as columns, the whole record as `json`, an index on latitude and longitude), `boundaries` (rings, holes, parts, water edge as JSON), `grids` (anchor, heading, cell size, bounds, `cell_record_version`, and the `rows` blob as bytes), and `nearby` (one row per item, indexed by beach). Rows go in id order and the file is vacuumed and gzipped with no name and mtime 0, so the same pack gives the same sha256. Reason: the index entry can then be published as is, and a phone compares one hash. Hawaii is 7.4 MB of SQLite, 2.2 MB gzipped.
- **Overrides are per state and applied at build.** `overrides/<st>.json` maps a beach id to any of `name`, `tier`, and `water_edge` (polylines of [lat, lng]), with a required `reason` and `date`; the file is validated on load and `overrides/hi.json` ships empty. A name is applied before scoring (a corrected name counts) and the OSM name is kept in the record's `override.osm_name`, so removing the override restores it without a re-pull. A tier is applied after scoring and wins, and sets `seed_space`. A water edge replaces the detected one, turns +y away from it (the side away from the beach's centre is water, `orientation` `override`), and is measured to for water distance; it is part of the geometry hash, so the grid is recomputed and its heights re-measured from the kept rasters. Ids that match no beach are listed in the manifest as `unmatched` and printed by build. Reason: the admin review map writes corrections that must survive every re-pull and must not need a code change.
- **Island lidar is read against its own flattened sea.** Where there is no NAVD 88 the terrain is read as local mean sea level, but 3DEP projects flatten the sea to a fixed value that need not be 0: Hawaii's 2020 Oahu and Maui lidar uses 0.00, the 2017 Hawaii Island lidar -0.40. `terrain_water_m` is now the median height 15 m beyond each column's lowest cell on the water side (probing from the outline's water edge landed on sand for beaches drawn seaward of the coastline), and per 3DEP project the most common water level of its sea beaches, when at least half of five or more share it to the centimetre, is taken as that project's mean sea level (`terrain_sea_level_m`), so mean high water there is that level plus the station's MHW above MSL (`tide_reference` "MHW over the flattened sea"). A measuring-rule version is part of the grid key, so a rule change re-measures every beach from the kept rasters, of this run or the state's earlier runs, before it touches the network. Reason: without it every Hawaii Island beach read 0.4 m low and came out mostly wash.
- **The pack hash counts the rules.** The manifest's top-level `pack_hash` covers the block hashes and also the shape settings (`derive`), the cell record version, and the terrain measuring version. Reason: a rule change rewrites grids without changing any source, and the index must still show a new pack.
- **The pull ranks beaches with their nearby items.** The quick assembly a pull uses to choose per-point targets now attaches nearby items (it takes a fraction of a second), so lifeguard posts and parking count before Census, NWS, and Wikipedia pick their primary and secondary beaches. Reason: without them the pull ranked 50 primary beaches where the build found 83, and 51 beaches went without county, place, and forecast zone.
- **Generated inland tiles are clipped, and a tile without beaches asks nothing more (20 October 2026).** Each 2° tile is clipped to the state's TIGER box grown by 0.03°, a little over the 2 km rule, and the nearby and water queries are not sent for a tile whose beach answer is empty (an empty answer is written in their place). Reason: Kansas reaches 40.003° N, so the unclipped grid pulled a whole row of Nebraska tiles, and most edge tiles of an inland state hold no beaches; at four to fifteen minutes per Overpass answer under load, the wasted queries were most of the run.
- **`landuse=reservoir` is lake water (20 October 2026).** The water query also returns `landuse=reservoir` ways and relations, and they are `lake`. Reason: the older tagging is still on many reservoirs, and an inland state's beaches are almost all on reservoirs.
- **Tide stations and buoys only where they describe the water (20 October 2026).** A lake or river beach takes no tide station (as before) and no buoy, except a Great Lakes beach, which may take a Great Lakes buoy. A beach with no water within 500 m takes a tide station or buoy only within 100 km, the reach the wave margin already uses; a sea beach takes the nearest at any distance. Reason: the nearest station to a Kansas beach is on the Gulf, 700 km away, and its datums would have put every Kansas cell hundreds of metres above mean high water.
- **A stale Overpass server is refused (20 October 2026).** An Overpass answer whose `timestamp_osm_base` is more than three days old is refused and the next endpoint asked, without retrying the stale one. Reason: on 21 October 2026 overpass.kumi.systems answered from May to July 2026 data, and in Kansas that dropped five of seven beaches in one tile with no error; the area and canary checks cannot see a server that is consistent but old. Any endpoint is accepted while its data is fresh; on 21 October only overpass-api.de was (overpass.kumi.systems was 98 days old, overpass.private.coffee 89), so a run with overpass-api.de unreachable waits for it rather than building from a mirror. The endpoints, in order: overpass-api.de, overpass.openstreetmap.fr (current on 21 October 2026 and answering when overpass-api.de refused this Mac's connections; a volunteer server with lower limits, so it comes second), then overpass.kumi.systems.
- **Nearby and water are asked by box, one half-degree cell at a time (21 October 2026).** The nearby and water queries no longer use `around`. Each tile is cut into 0.5° cells; only cells that a beach's bounds touch are asked, and in each the kind's own filters are asked over the boxes of that cell's beaches widened by 300 m (nearby) or 500 m (water), boxes merged while the union stays within 1.5 times their areas. The `around` canary becomes a count check: the server must see at least 90% of the cell's beaches on disk. Each cell's answer is kept under `<kind>/_parts/<tile>/` and the tile file is their merge (deduplicated, counts summed, the oldest `osm3s` kept). Box answers are a superset; the build already cuts nearby to 300 m from the outline and water to features whose box comes within 500 m of the beach's box. Reason: on California's first tile (San Diego, 342 beaches, 138 multipolygons) overpass-api.de's `around` found 37 of 342 beaches within 1 m of themselves on every try (4 of 47 on a small box), and the whole-tile query ran past the gateway timeout on overpass.kumi.systems and overpass.private.coffee; by box the densest cell answers in about 45 s.
- **A tidal datum the station does not publish comes from the nearest station that does (21 October 2026).** Mean sea level, NAVD 88, and HAT are each taken from the beach's tide station, or its reference station, else from the nearest station within 50 km (at most 10 asked) that publishes it, and `tide_datum_station_id`, `tide_navd88_station_id`, and `tide_hat_station_id` name which station gave each. NAVD 88 terrain without a NAVD 88 tie is no longer read as if NAVD 88 were mean sea level; its bands stay unknown. Reason: about a third of the California stations near beaches have no NAVD 88 tie or no HAT, and mean sea level sits about 0.8 m above NAVD 88 in Southern California, so the old fallback would have read those beaches 0.8 m high.
- **No buoy in reach still gives the default wave margin (21 October 2026).** When no beach in a run has a buoy within 100 km, the waves pull writes nothing, and every beach now still gets the default margin (0.3 m on a lake or river, 0.5 m otherwise) as long as the buoy table was pulled. Reason: in Kansas the empty waves folder left `wave_margin_m` null and `wet_limit_m` 0, so no lake cell could be wet.
- **A server without an area database is asked without areas (21 October 2026).** When an Overpass server answers the area checks with a missing area file (overpass.openstreetmap.fr has no areas), the beach query is asked again without them, and the answer must carry exactly as many beaches as the server's own `out count` of the same set. Reason: the areas were only ever a check on silent partial answers, the state comes from TIGER, and .fr was the only current server reachable on 21 October.
